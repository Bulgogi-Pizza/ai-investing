# 수식형 알고리즘과 과거 시뮬레이션

SOT: [next-phase-design.md](../planning/next-phase-design.md) 4절, 계획: [next-phase-plan.md](../planning/next-phase-plan.md) 7b. 구현: `src/lib/algo/`, 테스트: `tests/algo-*.test.ts`.

모두 순수 함수다. 네트워크, 시계, 저장소, 주문 코드가 없다. 같은 입력이면 같은 결과가 나온다. 서버, 화면, Firestore 연결은 이후 단계에서 이 라이브러리를 호출한다. 이 라이브러리는 주문을 내지 않는다.

## 입력

- 일봉 `DailyBar {date: 'YYYY-MM-DD', open, high, low, close, volume}`. 오래된 봉부터 정렬하고 날짜는 거래소 현지 날짜다. 토스 캔들은 `adjusted=true`로 요청하므로 분할은 이미 반영되어 있다고 가정한다.
- 가치 입력 `ValueSnapshot {filedAt, per, pbr, roe}`. 재무 라이브러리(5b)와는 따로 만들었으므로 이 최소 인터페이스만 정의했다. 재무 라이브러리의 시점별 행을 이 모양으로 바꾸는 어댑터가 연결 지점이다. `filedAt`은 공시일이고, 그 날짜 **다음 날 판단부터** 쓴다.
- 수급·뉴스 점수는 선택 입력(`external.supply`, `external.news`, 각각 [-1, 1])이다. 실전 판단에서는 받을 수 있지만 과거 시뮬레이션에는 쓰지 않는다.

## 신호 점수

모든 점수는 [-1, 1]이고, 데이터가 부족하면 `null`이다. `clamp(x)`는 -1과 1 사이로 자른다. 판단일 t의 입력은 직전 거래일(t-1)까지의 완결된 일봉과 판단 시점 가격(과거 시뮬레이션에서는 t일 시가)이다. 아래에서 "계열 S"는 완결 일봉의 종가들 뒤에 판단 시점 가격을 붙인 계열이다.

| 신호         | 공식                                                                                                                                                                                                                                                                                                                      | 기본값                                                                | 필요한 완결 봉 수           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------- |
| 추세 `trend` | 교차 = clamp((SMA빠름(S)/SMA느림(S) - 1) / crossScale), 위치 = clamp((가격/SMA느림(S) - 1) / priceScale), 방향 = (교차 + 위치) / 2. 강도 계수 f = 0.5 + 0.5 × clamp01(ADX / adxFull). 점수 = 방향 × f. | 수급·뉴스    | 계산하지 않는다. 입력 점수를 그대로 전달한다(범위 밖이면 오류)                                                                                                                                                                                                                                                            | -                                                                     | -                           |

## 종합과 결정

- 종합 점수 = Σ(가중치 × 점수) / Σ(가중치). 합은 점수가 있는 신호만 대상으로 하므로 `null` 신호의 가중치는 다시 나눠진다(재정규화).
- `null`인 신호가 가진 가중치가 설정된 전체 가중치의 **절반을 넘으면** 종합하지 않고 `hold`, 이유 `insufficient-data`로 한다. 정확히 절반은 판단한다.
- 점수 >= 매수 기준이면 `buy`, 점수 <= 매도 기준이면 `sell`, 그 사이는 `hold`. 결정은 `{action, score, reason, signals}` 모양이며 AI형도 같은 모양을 쓰게 한다.

`createAlgorithm(template, {name, market, symbols, budget}, overrides)`가 정의를 만들고 `validateAlgorithm`으로 검증한다. 정의는 모드와 무관하다(시뮬레이션, 모의, 실전이 같은 객체를 쓴다). `method`는 `'formula'`만 지원한다. 종목당 비중은 기본 예산 / 대상 종목 수(듀얼 모멘텀은 예산 / topN)이며 `positionFraction`으로 바꾼다.

## 체결 시점 모델

설계의 실행 주기(개장 직후 하루 한 번)와 같다.

1. t일 시가에 판단한다. 입력은 t-1일 종가까지의 일봉, 그 시점까지 공시된 재무, t일 시가다. t일의 고가·저가·종가·거래량은 읽지 않는다.
2. 주문은 시가 기준 지정가이며 t일 시가에 체결된다. 슬리피지 `slippageBps`는 불리한 방향으로 적용한다(매수 시가 × (1 + s), 매도 시가 × (1 - s)). 기본 0이다.
3. 수량은 정수 주(국내·미국 모두)다. 매수 수량 = floor(min(종목 한도, 현금) / (체결가 × (1 + 수수료율))). 종목 한도는 처음 운용 금액 기준으로 고정한다(복리 재투자 없음). 레버리지와 공매도는 없다. 이미 보유한 종목은 추가 매수하지 않는다.
4. 하루 처리 순서: 누적 손실 검사(시가 평가) → 모든 종목 판단 → 매도 먼저(종목 코드 순) → 매수(점수 높은 순, 같으면 종목 코드 순) → 종가 평가와 곡선 기록. 같은 날 매도 대금은 곧바로 매수에 쓸 수 있다(결제 지연은 반영하지 않는다).
5. 휴장일은 모든 대상 종목 일봉 날짜의 합집합으로 만든 달력으로 센다. 거래일 수(최소 보유 기간)는 이 달력 기준이다. 시작일을 주지 않으면 한 종목이라도 신호에 필요한 봉 수(`requiredBars`)를 채운 첫 날부터 시작한다. 시작일 이전 봉은 이력으로만 쓴다.

### 시점 누수 방지

- 구조: 판단 함수에는 `t`일 앞의 봉만 잘라서 넘긴다. t일에서는 시가만 가격으로 별도 전달한다. 가치 입력은 `filedAt`이 판단일보다 앞선 것만 쓴다(공시일 당일 판단은 쓰지 않는다).
- 검사: `computeSignalScores`는 판단일 이후 날짜의 봉이 들어오면 `look-ahead` 오류를 던진다.
- 예상 이익 통계는 판단일 이전에 닫힌 신호 왕복만 쓴다(아래).
- 지표는 최근 구간만 쓰도록 했다(ADX는 최근 140봉). 그래서 이력이 더 길거나 짧아도(충분하기만 하면) 같은 값이 나온다.
- 테스트(`tests/algo-lookahead.test.ts`): 임의의 판단일 이후 모든 봉(판단일 당일은 시가만 남기고 나머지)과 그 이후 공시를 마구 바꿔도 판단일까지의 결정, 체결, 자산 곡선이 같다. 수식형(예상 이익 무시·적용)과 듀얼 모멘텀을 모두 확인한다. 누수를 일부러 넣으면(시가 대신 종가 사용) 이 테스트가 실패하는 것도 확인했다.

## 비용

- 수수료: `commissionRate`(양쪽 체결금액 × 비율). 실행 때 토스 `/commissions` 값을 넣는다.
- 증권거래세: `sellTaxRate`(국내, 매도 체결금액 × 비율). 설정값이다.
- 양도소득세: `capitalGainsTax {rate, annualDeduction}`(미국). 달력 연도별로 그해 청산된 왕복의 순실현손익(매도대금 - 수수료 - 거래세 - 매수 원가와 매수 수수료)을 합산해 `max(0, 합계 - 공제) × 세율`을 구한다. 손실 이월은 반영하지 않는다. 세금은 그해 마지막 거래일 종가에 자산 곡선에서 차감하며(마지막 해는 실행 마지막 날), 매매에 쓰는 현금은 줄이지 않는다(세금은 운용 금액 밖에서 낸다고 본다). 설정 금액은 알고리즘 통화 기준이다.
- 환전은 비용이 아니다. 미국은 달러로 사고 달러로 판다(설계 확정).
- 세율을 코드에 넣지 않았다. 입력하지 않은 값은 0으로 계산하고 `costSettings.needsSetup`과 `warnings`에 "설정 필요"를 표시한다(국내: 수수료율·거래세율, 미국: 수수료율·양도세).
- 슬리피지는 체결가에 이미 들어 있으므로 비용 항목이 아니라 총수익에 반영된다. `totalReturn`은 명시 비용(수수료·세금) 차감 전, `netReturn`은 차감 후다. 둘의 차이가 `costs.total`이다.

## 예상 이익 규칙

- "신호 왕복": 매수 신호가 나온 날 시가(슬리피지 포함)에 사서, 같은 알고리즘이 처음으로 매도 신호를 낸 날(최소 보유 기간 이후)의 시가에 파는 가상 거래다. 종목마다 한 번에 하나만 연다. 실제 주문 여부, 예산, 거래 횟수 제한과 무관하게 **모든 매수 신호**에서 기록하므로, 규칙에 막혀 주문이 나가지 않는 동안에도 통계가 쌓인다. 기록은 총수익률(수수료·세금 전) = 매도가 / 매수가 - 1이다. 표본은 수수료와 세금을 **빼기 전** 값이므로, 주문 조건에서 아래의 명시 왕복 비용(2 × 수수료율 + 거래세율)과 비교한다. 슬리피지는 체결가에 이미 들어 있다. 끝까지 닫히지 않은 신호는 기록하지 않는다.
- 점수 구간: 매수 시점 종합 점수를 0.1 폭 구간으로 나눈다(`floor(score / 0.1)`, 점수 1은 마지막 구간).
- `expectedProfit(bucketStats, score, minSamples = 20)`: 점수가 속한 구간의 평균 총수익률. 표본이 `minSamples`개 미만이면 `null`이고 호출자는 주문하면 안 된다. 통계는 JSON으로 저장할 수 있고 `buildBucketStats(samples, {asOf})`로 특정 날짜 기준(그 날 전에 닫힌 표본만)으로 다시 만들 수 있다.
- 주문 조건: 예상 이익 > `2 × 수수료율 + 거래세율`. 같거나 작으면 `expected-profit-below-cost`, 기록 부족이면 `insufficient-history`로 보류한다. 양도소득세는 이 비교에 넣지 않는다.
- 워크포워드: 시뮬레이션 안에서 t일 판단은 t일 **이전에** 닫힌 신호 왕복(닫힌 날짜 < t)만 쓴다. 같은 날 닫힌 표본은 다음 날부터 보인다. 결과에 `heldBack {insufficientHistory, expectedBelowCost}`를 낸다. 값은 보류된 "신호 일수"다(같은 종목의 신호가 여러 날 이어지면 날마다 센다).
- 연구용 모드(`expectedProfit.mode: 'ignore'`): 규칙 없이 신호대로 거래한다. 결과에 `researchOnly: true`, `expectedProfitMode: 'ignored-for-research'`, 경고 문구가 붙으며 실전 가능 여부를 판단하는 데 쓰지 않는다.

## 결과

`runBacktest({algorithm, bars, values?, options?})`의 결과:

- `metrics`: 총수익 `totalReturn`(비용 전), `netReturn`(비용 후), `maxDrawdown`(최고점 대비 낙폭, 0 이상 비율, 시작 자산 포함), `volatility`(일별 자산 수익률의 표본 표준편차 × √252, 수익률 2개 미만이면 `null`), `trades`(체결 수), `roundTrips`, `winRate`(세금 전 순손익이 양수인 왕복 비율), `exposure`(일별 평가금액/자산의 평균), `daysInvested`(보유 중으로 끝난 날의 비율).
- `costs`: 수수료, 거래세, 양도세, 합계, 연도별 양도세 내역. 수수료·세금은 따로 보인다.
- `equityCurve`, `trades`, `roundTrips`, `openPositions`(끝까지 보유 중인 종목, 평가금액으로 곡선에 반영), `decisions`(`recordDecisions: true`일 때), `rejections`(막힌 주문 시도의 이유별 횟수), `stoppedOn`, `samples`와 `bucketStats`.
- `excludedSignals: ['supply', 'news']`: 항상 표시한다. 설정에 수급·뉴스 가중치가 있어도 시뮬레이션에서는 빼고 남은 신호의 가중치로 재정규화한다(`excludedSignalWeightShare`로 제외된 비중을 알린다). 과거 신호가 하나도 없으면 오류를 던진다.
- `warnings`: 설정 필요 항목, 수급·뉴스 제외, 연구용, 누적 손실 정지.

## 알려진 한계

- 생존 편향: 대상 종목 목록은 사용자가 지정하므로 지금 시점에서 고른 종목이면 과거 성과가 좋게 나온다. 상장폐지·거래정지 종목은 데이터에 없다.
- 장중 체결 없음: 시가 한 번에 전량 체결로 가정한다. 호가 단위(틱) 반올림, 부분 체결, 시초가 단일가의 체결 불확실성, 시가 갭의 유동성은 반영하지 않는다. 실전 판단은 개장 직후 현재가를 쓰므로 시가와 다를 수 있다.
- 슬리피지는 단일 비율이다. 주문 수량에 따른 시장 충격은 모른다.
- 분할·배당: 분할은 일봉이 보정되어 있을 때만 맞다(토스 `adjusted=true`). 배당금은 반영하지 않는다.
- 결제 지연(T+2)과 환전 시차는 반영하지 않는다.
- 거래대금은 종가 × 거래량으로 근사한다.
- 1억 원 이상 매수는 거부한다. 매도는 1억 원 미만으로 나눠 내므로 갇히지 않지만 분할 매도는 여러 날 걸릴 수 있고, 그동안 가격이 움직인다.
- 미국 1억 원 환산 상한은 환율이 필요해 기본 검사가 없다.
- 손실 정지 뒤에는 보유분을 정리하지 않는다. 설계의 "자동 정지"를 따랐고 청산 여부는 사용자 판단이다.
- 가치 신호는 공시 행 사이에는 값이 바뀌지 않는다. 이력이 짧은 종목은 `null`이다.
- 세율·세금 규칙(손실 이월, 공제)은 설정과 단순 규칙이다. 신고용 계산이 아니다.
- 수급·뉴스·시장 지표 신호는 과거 시뮬레이션에서 쓸 수 없다. 앞으로 저장한 기간만큼 전체 신호 시뮬레이션이 가능해진다(설계 4절).
- 이 문서의 결과는 과거 시뮬레이션이며 미래 수익을 보장하지 않는다.

AI형은 시뮬레이션 모드를 가질 수 없고(모의부터) 과거 시뮬레이션을 지원하지 않는다. 수정은 `version`을 보내야 하며 어긋나면 409 `VERSION_CONFLICT`.

**실전은 막혀 있다.** `mode: 'live'`는 생성·수정 어디서든 서버가 가장 먼저 403 `LIVE_NOT_AVAILABLE`("실전 운용은 주문 기능 단계(7d–7f) 이후에 켤 수 있습니다.")로 거부하고 아무것도 저장하지 않는다. 7f가 `createAlgorithmsRouter`의 `liveEnabled`(생성자 옵션, 환경변수 아님, 운영 코드는 설정하지 않는다)를 켠다. 그때를 위해 "실전 알고리즘끼리 대상 종목 겹침 금지"(409 `LIVE_TARGET_OVERLAP`, 충돌한 알고리즘 이름과 종목을 메시지에 담음)는 이미 구현·테스트되어 있고 테스트만 이 옵션을 켠다. 화면의 실전 모드 선택은 비활성이며 이유를 적는다. 모의(`paper`)는 저장되지만 판단 작업(7c)이 없으므로 아직 가상 기록은 쌓이지 않는다. 이 라우터에는 토스 주문 호출이 없고 테스트의 가짜 토스 전송은 주문 경로가 호출되면 실패한다.

**긴급 정지·알림.** 정지 켜기는 확인 대화상자 한 번 뒤 바로 적용되고 알림이 없다(위험을 줄이는 동작). 해제는 추가 인증 없이 되지만 `setting-risk-increase`(`emergency-stop-released`)를 `NotificationService`로 보낸다. 운용 금액을 기존 값보다 올리면 `budget-raised`를 보낸다(없던 값을 처음 넣거나 낮추는 것은 알리지 않는다). 알림 서비스는 던지지 않으므로 텔레그램 실패·미설정이 변경을 막지 않고, 응답의 `notification: {status: sent|failed|disabled, failureCode?}`로 화면이 정확히 말한다. 플래그는 이 단계에서 아무 작업도 읽지 않는다(작업은 7c 이후). 읽는 쪽은 주문 직전마다 `algorithmControl/global`을 다시 읽어야 한다(7e).

### 시뮬레이션 실행

서버가 저장된 정의로 7b `runBacktest`를 돌린다(요청 본문으로 정의를 받지 않는다).

- 데이터: 기존 토스 캔들 어댑터(`interval=1d`, `adjusted=true`)로 종목마다 **최대 200봉 한 번**. 어댑터에 `before`/`nextBefore` 페이지 조회가 아직 없어(구현 전 확인 목록의 "캔들 과거 범위" 미확인) 약 9~10개월만 반영하며 결과 경고와 화면에 그대로 적는다. 그래서 252일 기본 듀얼 모멘텀은 422 `INSUFFICIENT_HISTORY`로 설명하고 기간을 줄이라고(예: 126) 안내한다. 일봉 날짜는 제공자 타임스탬프의 날짜 부분이며 거래소 현지 날짜라는 가정은 실호출로 확인하지 않았다. 해당 시장의 오늘 날짜 봉은 진행 중일 수 있어 제외하고 경고한다. 캔들 통화가 알고리즘 통화와 다르면 422 `CURRENCY_MISMATCH`.
- 비용: 수수료율은 토스 `/commissions` 어댑터가 아직 없어 `algorithmSettings/costs`의 직접 입력을 쓴다. 입력이 없으면 7b가 0으로 계산하며 결과에 "설정 필요" 경고와 `costSettings.needsSetup`을 낸다.
- 가치 신호: 재무 연결 전이라 정의에서 빼고 나머지 신호로 계산하며 `disabledSignals: ['value']`와 경고를 낸다. 남는 신호가 없으면 422 `NO_HISTORICAL_SIGNAL`. 수급·뉴스는 7b대로 항상 제외(`excludedSignals`).
- 운용 금액이 비어 있으면 기본 금액(KRW 1천만, USD 1만)을 가정하고 `budgetAssumed: true`로 표시한다.
- 한도: 사용자별 분당 6회(429 `BACKTEST_RATE_LIMITED`), 동시 실행 2개(429 `BACKTEST_BUSY`), 대상 종목 10개까지(초과는 잘라서 돌리지 않고 400 `BACKTEST_TOO_MANY_SYMBOLS`), 봉 200개, 시세 조회 25초 제한(504 `BACKTEST_TIMEOUT`), 계산 후 30초를 넘기면 결과를 버린다(계산 자체는 입력 상한으로 제한되며 중간에 끊지 못한다).
- 응답: `metrics`, `costs`(수수료·거래세·양도세·합계 따로), `costSettings`, `heldBack`, `excludedSignals`, `disabledSignals`, 자산 곡선(최대 120점으로 줄임), 가상 매매(최근 100건, `tradeCount`·`tradesTruncated`), `openPositions`, `warnings`, `data`(출처, 종목별 봉 수, 기간). `samples`·`decisions`는 보내지 않는다. 항상 `simulation: true`.

### 작업 흐름

1. `ALGO_MARKET`(KR/US)의 오늘 캘린더를 읽어 정규장 개장 후 20분 이내(`ALGO_OPEN_WINDOW_MINUTES`로 조정)일 때만 진행한다. 휴장은 `algorithmRuns/{market}_{date}`에 `skipped`로 한 번 남긴다. 미국은 22:35·23:35 KST 두 슬롯이 모두 도는데, 서머타임에는 22:35만(개장 22:30), 그 외에는 23:35만(개장 23:30) 창 안에 들어온다. 다른 슬롯은 아무것도 하지 않는다(`OUTSIDE_OPEN_WINDOW`/`SESSION_NOT_OPEN_YET`).
2. `algorithmRuns/{market}_{date}`로 중복을 막는다. `complete`면 건너뛰고, 신선한 `running`이면 건너뛰고, 낡은 `running`·`partial`·`failed`는 인수한다(이미 반영된 알고리즘은 아래 멱등 규칙으로 건너뛴다).
3. 알고리즘마다(직렬): **긴급 정지 플래그를 그 알고리즘 직전에 다시 읽는다.** 켜져 있으면 `skipped EMERGENCY_STOP`만 기록하고 아무것도 하지 않는다(플래그를 못 읽으면 `CONTROL_UNAVAILABLE`로 건너뜀, 닫힌 쪽으로 실패). 이어서 장부가 이미 이번 실행을 반영했으면 `RUN_ALREADY_APPLIED`, 정지 상태면 `PAPER_STOPPED`, AI형인데 꺼져 있으면 `AI_APPROVAL_PENDING`(이유 "AI 비용 승인 대기").
4. 데이터: 대상 종목과 아직 보유 중인 종목의 일봉을 `before` 페이지로 모은다(기본 500봉, 필요 길이+30 중 큰 값). 신선도: 마지막 완결 일봉이 직전 거래일 이후여야 하고, 현재가의 시세 시각이 60초 이내(`maxQuoteAgeMs`)이며 통화가 맞아야 한다. 조건을 못 채운 종목은 그날 판단하지 않고 이유를 `notes`에 남긴다. 신선한 대상이 하나도 없으면 장부를 건드리지 않고 `failed DATA_UNAVAILABLE`(같은 날 다음 슬롯이 다시 시도할 수 있다).
5. 신호: 가치는 재무 어댑터가 연결되기 전이라 **끄고 "가치: 재무 데이터 연결 전이라 제외"로 표시**한다(`values` 의존성을 주입하면 켜진다). 수급은 국내 종목만, 최근 5거래일 중 3일 이상의 `investorTrading` 스냅샷이 있을 때만 쓰고 없으면 제외 표시한다. 뉴스는 점수화 규칙이 아직 없어 항상 제외 표시한다. 쓸 신호가 하나도 없으면 `NO_USABLE_SIGNAL`.
6. 같은 엔진(`decideFormula`/`decideDualMomentum`)과 같은 안전장치 함수(`checkOrder`)로 판단하고 가상 체결한다. 결과를 장부와 `paperTrades`에 저장한 **뒤에** 체결마다 텔레그램 `fill`(mode `paper`, "가상 체결")을 보낸다. 손실 정지가 걸리면 `algorithm-auto-stop`(mode `paper`)을 보낸다. 작업이 실패·일부 실패하면 `job-failure`를 보낸다.

### 안전장치 의미: 시뮬레이션과 같은 점, 다른 점

`runPaperDay`는 `runBacktest`의 하루 반복을 영속 상태로 옮긴 것이다. `tests/algo-paper.test.ts`가 합성 시세 140일을 두 경로로 돌려 **체결 날짜·수량·가격, 수수료·거래세, 왕복 수, 신호 단위 표본, 거부 횟수, 미청산 포지션이 모두 같음**을 확인한다(예상 이익 규칙과 슬리피지 포함).

### AI형

판단 계약(`src/server/algorithm-ai.ts`)은 설명 계약(`ai.ts`)과 별개다. 입력은 종목별 신호 요약(종목 코드, 현재가, 보유 여부·보유 거래일, 신호 점수)뿐이고 계좌·수량·금액·알고리즘 이름·사용자 ID는 보내지 않는다(12,000바이트 제한). 출력은 `{decisions:[{symbol, decision: buy|sell|hold, reasons: 1~3개, expectedReturn:{low,high}}]}`이며 **요청한 종목이 정확히 한 번씩**, 닫힌 값 집합, `-1 ≤ low ≤ high ≤ 1`, 추가 필드 없음, 근거 문장은 설명 계약과 같은 텍스트 안전 검사(URL·HTML·이메일·8자리 이상 숫자·제어 문자 거부)를 통과해야 한다. 하나라도 어긋나면 전체를 버리고 `failed AI_OUTPUT_INVALID`, 거래 없음. 예상 수익률은 범위의 중앙값을 "예상 이익"으로 써서 같은 규칙(`> 왕복 비용`)을 적용한다(제안). 호출은 알고리즘당 하루 1회이며 기능별 한도(`aiUsage/algorithm_{KST날짜}`, 하루 12회, 호출 직전 차감·실패해도 환불 없음)를 넘으면 `AI_QUOTA_EXCEEDED`. 시도는 자동 재시도하지 않는다. 생각(thinking) 토큰 한도는 공식 설정 방식을 확인하지 못해 기본으로 보내지 않고(`ALGO_AI_THINKING_BUDGET`을 줄 때만 `thinkingConfig.thinkingBudget`), 출력 한도만 4096으로 넉넉히 둔다.

**꺼짐 장치**: 작업은 환경 변수 `ALGO_AI_ENABLED`가 정확히 문자열 `true`일 때만 AI를 켠다(`true`가 아닌 모든 값·미설정은 꺼짐). 배포 워크플로가 `ALGO_AI_ENABLED=false`를 명시한다. 꺼져 있으면 AI형 알고리즘은 모델 호출도, 시세 조회도, 장부 생성도 없이 실행 기록에 `skipped AI_APPROVAL_PENDING`(이유 "AI 비용 승인 대기")만 남기고 화면에도 같은 문구를 보인다. 비용 승인이 나면 값을 `true`로 바꿔 작업을 다시 배포한다([예약 작업](../operations/jobs.md#모의-운용-작업-algo-paper)).

### API와 화면

- `GET /api/algorithms/:id/paper`(소유자 전용, 같은 `ownerGate`·세션 인증, `Cache-Control: no-store`): `{virtual:true, algorithm, ai, ledger, metrics, equityCurve(120점), trades(최근 50), runs(이 알고리즘의 최근 20회), notes}`. 장부가 없으면 `ledger/metrics:null`이고 숫자를 만들어 내지 않는다. `metrics`는 모의 시작 이후의 총수익(비용 차감 전), 수수료·거래세·양도세·합계와 슬리피지(체결가에 이미 반영, 합계에 불포함), 비용 차감 후 수익, 최대 낙폭, 변동성(연환산), 가상 매매 수·왕복 수·승률, 실현·평가 손익이다. 저장소 오류는 503 `PAPER_UNAVAILABLE`(세부 없음).
- 화면: 알고리즘 탭의 "모의 운용" 구역(과거 시뮬레이션 아래). 호박색 "가상 기록" 배지, 모든 지표 이름에 "(가상)", 가상 보유·가상 체결 내역(가상 매수/가상 매도)·판단 기록(건너뜀 이유, 제외한 신호, 보류 횟수)·정지 표시·"AI 비용 승인 대기" 표시. 장부가 없으면 빈 상태만 보인다.
- 차트 "내 매매" 마커용 읽기 함수: `listFills(repository, symbol): Promise<ChartFill[]>`(`src/server/paper.ts`). `ChartFill = {date, at, side, quantity, price, algorithmId, mode}`(`mode`는 지금 `'paper'`뿐, 실전 체결이 생기면 `'live'`로 같은 모양을 쓴다). 잘못된 종목 코드나 저장소 오류는 `[]`. 앱은 `createApp({paperRepository})`로 같은 저장소를 받는다.

## 7f: 실전 운용 (구현 2026-10-21, 운영 적용 전, 실주문 미검증)

주문 기반([trading.md](trading.md))을 알고리즘에 연결한 단계다. 실제 돈이 걸리므로 **실제로 주문이 나간 적이 없고**, 아래는 합성 테스트로만 확인했다.

### 켜는 방법과 조건

- `LIVE_NOT_AVAILABLE` 막힘을 없앴다. `algorithmLiveEnabled`(기본 true, `false`면 모든 실전 저장을 403으로 거부하는 배포 스위치)만 남았다. 실제 주문이 나가는지는 실전 작업의 킬 스위치와 Scheduler 상태가 정한다.
- 알고리즘은 **만든 뒤** "실전 운용" 패널의 "실전 켜기…"로만 켠다. `POST /api/algorithms`에 `mode: live`를 보내면 400 `LIVE_REQUIRES_EXISTING`. 모의→실전 전환 `PUT`은 본문에 `liveConfirm: true`가 있어야 한다(없으면 400 `LIVE_CONFIRM_REQUIRED`; 일반 폼이 우연히 실전으로 저장하지 못하게 하는 장치이지 인증이 아니다).
- 실전에는 통화별 운용 금액이 필수다(400 `LIVE_BUDGET_REQUIRED`, 실전 알고리즘이 금액을 지우는 저장도 같다). 가치 신호(가중치 > 0)는 재무 어댑터가 없어 실전에서 쓸 수 없다(400 `LIVE_VALUE_SIGNAL_UNSUPPORTED`; 설계 안전장치 6). 실전 대상 종목 겹침 금지(기존 규칙)는 그대로다.
- 실전 중인 알고리즘은 삭제할 수 없다(409 `LIVE_ACTIVE`). 모의·시뮬레이션으로 바꾸는 것은 위험을 줄이는 동작이라 확인·알림 없이 된다(보유 수량·접수된 주문은 자동으로 정리되지 않는다는 안내를 확인창에 띄운다).
- 실전 켜기와 운용 금액 상향은 **텔레그램 알림이 설정되어 있어야** 한다(없으면 409 `ALERTS_NOT_CONFIGURED`): 사용자가 추가 인증을 두지 않은 대신 이 알림에 기대기 때문이다.
- 실전 알고리즘의 대상 종목·기준값·가중치·포지션 크기(듀얼 모멘텀 설정)·방식·템플릿을 바꾸면 `live-strategy-changed`를 알린다. 이름만 바꾸는 저장은 알리지 않는다. 모의 시작 뒤에 전략이 바뀌면 "실전 운용"의 모의 요약에 **"변경 전 기록"**이 붙는다(`strategyChangedAt`; 기록을 지우지는 않는다).
- 추가 인증은 없다(사용자 결정). 켜는 즉시 `setting-risk-increase`(`live-enabled`)를 텔레그램으로 보낸다. 응답의 `notifications: [{change, status}]`로 화면이 알림 결과를 정확히 말한다.

### 안전장치 설정 (`algorithmSettings/safeguards`, `PUT /api/algorithm-settings/safeguards`)

알고리즘당 하루 최대 주문 3, 전체 10, 최소 보유 5거래일, 누적 손실 정지 −20%, 최소 평균 거래대금 국내 10억 원·미국 500만 달러가 기본값이다(`defaultSafeguardSettings`). 범위: 하루 주문 1–20·전체 1–50, 보유 0–60거래일, 손실 정지 1–50%. 위험을 늘리는 변경(하루 주문·전체 주문 상향, 최소 보유 단축, 손실 정지 완화, 거래대금 기준 하향)은 종류마다 한 번씩 `setting-risk-increase`(`max-orders-raised`, `min-holding-lowered`, `loss-stop-loosened`, `liquidity-lowered`)를 보내고, 줄이는 변경은 알리지 않는다. 비교 기준은 직전 저장값(없으면 기본값)이다. **1억 원 상한과 현재가 60초는 고정이며 설정에 없다**(알 수 없는 키는 저장하지 않는다). 저장된 문서가 형식에 맞지 않으면 읽기가 던지고 실전 작업은 모든 알고리즘을 실패 처리한다(안전장치가 조용히 느슨해지지 않는다). 그 상태에서 저장하면 값이 기본값과 같아도 **항상 기록해 바로잡는다**. 변경 이력 종류 `safeguards-updated`.

### 화면 (내 자산 > 알고리즘 > "실전 운용")

- 실전 켜기: 모의 요약(모의 기간, 가상 왕복 횟수, 비용 차감 후 수익, 최대 낙폭), "기록 부족으로 주문 보류" 설명(시스템이 정한 최소 기간·성과 기준이 없고 사용자가 판단한다는 점 포함), 운용 금액, 켜기 전 필요한 조건 목록, 확인창(실제 돈, 추가 인증 없음, 텔레그램 알림, 운영자가 일정을 켜야 주문이 나감).
- 상태: 주문 권한 확인 결과(미확인/통과/실패 항목과 권한 거부 여부 + WTS 설정 확인 안내), **"실전 일정이 아직 꺼져 있어 주문이 나가지 않습니다 — 운영자가 일정을 켜야 합니다."**(실전 작업 하트비트가 없거나 4일보다 오래되면), 마지막 실행이 실패·일부 실패면 오류 색, 긴급 정지, 알고리즘 자동 정지와 사유(+ "정지 해제": 확인창, 텔레그램, 이력), 접수 여부 미확인 주문(각 주문에 "미확인 주문 정리…": 토스증권 앱에서 확인한 결과를 기록, 증권사에는 보내지 않음), AI 승인 대기. 자동 정지 안내에는 "정지해도 보유 종목은 자동으로 팔지 않으니 직접 관리하세요"가 들어 있다.
- 실제 보유, 실제 주문(`실제 매수`·`실제 매도` 배지, 모의의 `가상`과 섞이지 않음), 보류·차단 기록(한국어 사유). 첫 실전 주문이 거부되어 정지되면 정지 사유로 보인다.
- 종목 분석 차트의 체결 마커는 `CombinedAlgorithmFills`(모의 `paperTrades` + 실전 `liveOrders`의 체결 수량, 모드 `live`)를 쓴다. 한쪽 저장소가 실패해도 다른 쪽 마커는 그린다.
- 안전장치 설정 카드(고정 한도 표시 포함).

### 확인하지 못한 것 (7f)

실주문·실제 체결, `X-Tossinvest-Account`를 시세·가격 제한 같은 계좌 불필요 엔드포인트에 붙여도 되는지, `/exchange-rate`의 `validFrom`/`validUntil` 의미(현재 유효 구간 안이면 "지금 관측"으로 취급), 국내 호가 단위 400 응답의 실제 형태, 실제 `/prices` 시각의 신선도, 장 시작 직후 20분 창에서 실제 호출 한도 충분 여부, `unknown` 주문의 사람이 해소하는 경로.
